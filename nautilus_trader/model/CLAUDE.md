# Domain Model (`nautilus_trader/model/`)

Trading-domain-agnostic model: value objects, identifiers, instruments, orders, positions, events, market data, and order books. Designed so that many system implementations could be built around it.

## Language Boundary

Everything performance-critical is **Cython (.pyx/.pxd)**, delegating construction and validation to **Rust** via C FFI (`core/rust/model.pxd`, auto-generated by cbindgen). Pure Python files are limited to: `enums.py` (re-exports + str converters), `currencies.py` (dual-registration helper), `venues.py` (pre-built Venue constants), `custom.py` (`@customdataclass` decorator), `greeks_data.py` (`GreeksData`).

## Fixed-Point Precision (Critical Design Choice)

`Price`, `Quantity`, `Money` store values as **raw integers**, not floats. This eliminates floating-point rounding errors across the entire trading pipeline.

Two compile-time modes controlled by `HIGH_PRECISION` in `model.pxd`:
- **High precision** (default): 128-bit, `FIXED_PRECISION=16`, max price ~17 trillion
- **Standard precision**: 64-bit, `FIXED_PRECISION=9`, max price ~9.2 billion

All arithmetic comparisons operate on raw integers directly -- no float conversion.

**Construction convention**: Prefer `Price.from_str("1.5000")` over `Price(1.5, 4)` -- the former infers precision from decimal places. For internal fast paths, use `from_raw_c(raw, precision)` to skip validation.

## Key Design Points by Submodule

### Value Objects → `objects.pyx`
- `Price` allows negative (options); `Quantity` is non-negative only. `Quantity.saturating_sub` floors at zero instead of raising.
- `Money` couples amount with `Currency`; all arithmetic checks matching currency codes.
- `Currency.from_str("ETH")` auto-creates a crypto currency with precision 8 in non-strict mode.
- `AccountBalance`, `MarginBalance` are composite value objects.

### Identifiers → `identifiers.pyx`
All inherit from `Identifier` base, each wrapping a Rust `_mem` struct.
- `InstrumentId` = `Symbol` + `Venue` (e.g. `BTCUSDT.BINANCE`)
- `ClientOrderId` vs `VenueOrderId` -- client-side vs exchange-assigned; do not confuse
- `PositionId` can be virtual (`is_virtual_c`)
- `Symbol` supports composite symbols (`is_composite`) and root extraction
- Generic spread ID functions at module level build/parse multi-leg instrument IDs

### Instruments → `instruments/`
Base class `Instrument` (→ `base.pyx`) extends `Data`. 18 instrument classes follow a consistent pattern: `.pxd` declares cdef class, `.pyx` implements constructor + `from_dict_c`/`to_dict_c`.

Key sets in `base.pyx` for classification logic:
- `EXPIRING_INSTRUMENT_CLASSES` -- futures, options, spreads
- `NEGATIVE_PRICE_INSTRUMENT_CLASSES` -- options, futures spreads, option spreads

`Instrument.set_tick_scheme(name)` loads a tick scheme for price navigation (`next_bid_price`, `next_ask_price`). `make_price(value)` / `make_qty(value)` construct properly-precision'd value objects for the instrument.

`instruments_from_pyo3()` in `base.pyx` dispatches to the correct subclass from a PyO3 instrument list.

`SyntheticInstrument` (→ `synthetic.pyx`) is composed of legs with weights, computed from component instruments.

### Orders → `orders/`
Base class `Order` (→ `base.pyx`) manages lifecycle via FSM (`core.fsm`). Orders are **event-sourced**: `apply(OrderEvent)` transitions state. Order stores complete event history.

`OrderUnpacker` (→ `unpacker.pyx`) reconstructs an `Order` subclass from serialized `OrderInitialized` event's `options` dict, dispatching by `OrderType`.

Important classification sets in `base.pyx`: `STOP_ORDER_TYPES`, `LIMIT_ORDER_TYPES`, `TRIGGERABLE_ORDER_TYPES`, `CANCELLABLE_ORDER_STATUSES`, `LOCAL_ACTIVE_ORDER_STATUSES`.

### Events → `events/`
Three categories, all extend `Event` (from `core.message`):
- **Order events** (→ `order.pyx`): `OrderInitialized` through `OrderFilled`
- **Position events** (→ `position.pyx`): `PositionOpened`, `PositionChanged`, `PositionClosed`, `PositionAdjusted`
- **Account events** (→ `account.pyx`): `AccountState`

Events are immutable records of state transitions. Some (`OrderInitialized`, `OrderCanceled`, `OrderExpired`) store fields as Python objects rather than Rust `_mem` structs because they carry richer data.

### Position → `position.pyx`
Handles inverse instruments (`is_inverse`), cross-currency PnL, and netting vs hedging OMS semantics.

### Market Data → `data.pyx`
All types extend `Data`. Key non-obvious points:
- `BarType` combines instrument ID + bar spec + aggregation source + price type
- `OrderBookDeltas` supports capsule-based zero-copy transfer
- `capsule_to_list` / `pyo3_list_to_data_list` convert PyO3 capsule payloads into Python lists of Cython data objects (data engine fast path)

### Order Book → `book.pyx`
Wraps a Rust `OrderBook_API` struct. Supports L1_MBP, L2_MBP, L3_MBO. `should_handle_own_book_order` determines if an order should be tracked (only priced, non-IOC/FOK orders).

### Tick Scheme → `tick_scheme/`
`FixedTickScheme` -- uniform tick increment (forex, crypto). `TieredTickScheme` -- tick size varies by price level (some equities), pre-computes all valid ticks from `(start, stop, step)` tiers. Registered globally in `TICK_SCHEMES` dict.

## Module Boundary

**What belongs here**: Pure domain model -- state, value objects, identifiers, instruments, order/position lifecycle, market data types. No infrastructure, no networking, no execution routing.

**What does NOT belong here**:
- Execution engine logic → `execution/`
- Data aggregation engines → `data/`
- Adapter-specific instrument/order builders → `adapters/`
- Cache/persistence → `cache/`
- Serialization wire formats → `serialization/`

## Conventions When Modifying

- Every `.pyx` must have a matching `.pxd` declaring `cdef` class members and `cdef`/`cpdef` methods.
- New instrument types: add `.pxd`/`.pyx` pair, import in `instruments/base.pyx` and `instruments/__init__.py`.
- New order types: extend `Order`, add type to `OrderType` in Rust, update `OrderUnpacker`.
- Value objects are immutable after construction. State transitions happen via event application only.
- Validation uses `Condition` (from `core.correctness`) in constructors.
- Serialization uses `from_dict_c` / `to_dict_c` pattern (Cython `cdef static` methods).
- Timestamps are always `uint64_t` nanoseconds (UNIX epoch).
